# 115 扫码授权与连接管理

## Goal

为单人自托管部署提供一条可在管理后台完成的 115 网盘连接流程：管理员发起扫码、观察授权状态、完成连接验证，并让后续文件浏览、媒体库和 STRM 模块通过稳定连接 ID 使用服务端保存的凭据。

## Background and confirmed facts

- 项目已经完成单管理员登录与受保护管理路由；115 授权应发生在管理员登录之后，且不得与管理会话或未来播放凭据混用。
- 当前 `backend/internal/adapter/drive115` 与 `frontend/src/features/connections` 仍是占位目录，OpenAPI 中没有连接接口，基线迁移也没有业务表。
- 数据库设计已经确定首版只允许一个活动 115 连接。重新授权沿用稳定连接 ID；如果验证出的远端账号身份改变，必须阻断静默复用。
- 外部凭据以明文 JSON 保存在服务端 `connections.credential_json`；本次明确不做凭据加密或主密钥配置。凭据不得进入浏览器存储、URL、日志、任务快照或 API 响应；数据库与备份因此属于敏感凭据资产。
- GitHub 调研表明，现有扫码方案主要分为两类：
  - Cookie 扫码：获取二维码会话，轮询 waiting / scanned / allowed / expired / canceled，确认后按设备类型换取 `UID/CID/SEID/KID`。`SheltonZhu/115driver` 提供 MIT 许可的 Go 实现；OpenList、115-MCP-Server 和 115StrmTool 也采用或封装了类似流程。
  - 官方开放平台 OAuth：保存 access token 与单次轮换的 refresh token，需要自有或第三方应用信息。公开项目文档中的移动端 PKCE 扫码仍标记为未完成；借用第三方公共授权服务会增加信任和可用性依赖。
- Cookie 扫码的设备选择会影响同账号已有登录。社区实现普遍建议使用 `alipaymini` 或 `wechatmini`，避免默认 Web/Android/iOS 登录挤掉常用设备；Windows、macOS、Linux 设备类型已不可用或不稳定。
- 用户已确定首版采用 Cookie 扫码，并要求 Web 设备方式也属于受支持选项；首版设备范围为 `web`、`alipaymini`、`wechatmini`。
- 用户已确定连接页默认选择 `web`；`alipaymini` 和 `wechatmini` 作为可选设备方式。Web 默认项旁仍需展示可能影响现有网页登录或触发 IP 登录异常的提示。
- 本任务的 GitHub 参考与证据已记录在 `research/github-115-auth.md`。参考实现用于验证协议和状态边界；不得直接复制与本项目 Apache-2.0 不兼容的 AGPL/GPL 代码。

## Requirements

- R1：管理后台提供一个活动 115 连接的查看、首次授权和重新授权入口；连接拥有稳定 ID、显示名、已验证账号身份、摘要状态、能力证据和更新时间。
- R2：扫码流程必须由后端访问 115，前端只接收显示二维码所需的非凭据数据和规范化状态；前端不得直接调用 115 域名，也不得接收最终 Cookie/token。管理员可以在发起扫码前选择 `web`、`alipaymini` 或 `wechatmini` 设备方式，默认选择 `web`，UI 对 Web 方式可能影响现有网页登录或触发 IP 登录异常给出明确提示。
- R3：扫码会话至少区分创建中、等待扫码、已扫码待确认、已授权、已过期、已取消和失败；会话有明确过期时间，重复查询与重复完成操作必须安全，页面刷新后的行为要有确定约定。
- R4：授权成功后，后端先验证远端登录和账号身份，再将凭据以明文 JSON 在同一业务操作中创建或更新连接；验证或持久化失败不能留下“已连接”的假状态。
- R5：重新授权沿用现有连接 ID。新凭据验证出的账号与现有 `external_account_id` 不一致时，必须停止替换并向管理员明确提示，不得让已有媒体库静默指向另一个账号。
- R6：连接 API 受现有管理员会话与 CSRF 保护。允许把 115 上游错误码和可读错误消息返回前端；必须提取必要错误字段并脱敏，不能返回 Cookie、token、二维码签名、完整二维码会话参数、原始响应体或解密后的凭据。
- R7：连接凭据以明文 JSON 保存，不要求主密钥，也不生成临时密钥；读取凭据仅限后端连接服务，数据库与备份需按可恢复外部登录凭据的敏感数据进行保护。
- R8：连接验证至少产生账户身份和“可读取根目录”能力证据；状态要区分未检查、可用、失效、受限和未知，不能把网络错误当成凭据失效。
- R9：实现通过项目自己的 115 adapter 边界暴露能力，业务 Service 不依赖第三方 SDK 类型。是否采用 `115driver` 作为内部依赖由技术设计确认，并固定版本、封装错误与 HTTP 超时。
- R10：补充部署配置与运维说明，包括凭据明文存储与数据库/备份保护、重新授权、账号不一致、扫码过期和凭据失效处理。
- R11：首版不提供断开或删除连接；连接页只提供查看状态、只读连接测试和重新授权。重新授权在账号一致时覆盖原凭据并保留连接 ID。
- R12：连接管理不是独立侧边导航项；在设置项下方展示 115 授权卡片，未授权时提供连接入口，已授权时展示账号名、会员状态和网盘容量摘要。
- R13：授权成功时保存非敏感账号资料快照，并允许管理员手动刷新。资料或容量字段不可用时明确显示未知，不能因此撤销已验证连接或暴露凭据。
- R14：账号资料展示参考用户提供的 115 信息页：头像、用户名、UID、Cookie 授权方式、可确认的 VIP 状态和到期时间、已用和总容量/进度，以及当前 SDK 可读取的设备数。只显示当前 Cookie 接口实际提供的等级名称；SDK 返回的内部数值只用于状态判断，不显示为会员等级，也不映射成官方名称。Cookie 接口不提供的 VIP 名称、第三方畅用权益等，不得根据不同认证方式的 Open API 示例伪造。
- R15：扫码创建/轮询/完成、连接验证、资料刷新和只读测试等 115 上游调用失败时，向管理员返回可操作的上游错误详情；非 115 错误继续使用本项目稳定错误类别。

## Acceptance Criteria

- [x] AC1（R1/R2/R3）：已登录管理员能在连接页选择 Web、支付宝小程序或微信小程序设备方式并发起扫码，看见二维码以及等待、已扫码、成功、过期、取消和失败等状态；选择 Web 时能看到设备登录影响提示；未登录用户不能调用相关接口。
- [x] AC2（R3）：二维码过期或取消后不会生成连接；重新发起会得到独立会话，重复轮询和重复完成不会创建多个活动 115 连接或泄漏凭据。
- [x] AC3（R4/R8）：扫码确认后，服务端验证账号身份和根目录读取能力，成功时显示可用连接摘要；网络失败、115 拒绝和验证不完整分别保留可诊断的非秘密状态。
- [x] AC4（R4/R6/R7）：SQLite 中保存服务端使用的明文凭据 JSON；API、浏览器存储、URL、日志和错误中没有 Cookie/token。部署无需凭据主密钥。
- [x] AC5（R5）：同账号重新授权沿用连接 ID 并替换凭据 JSON、清空旧能力后重测；不同账号授权被阻断，旧凭据和已有依赖保持不变。
- [x] AC6（R8/R9）：后续模块可通过项目 adapter 使用连接，不需要理解二维码会话或第三方 SDK 类型；连接测试只验证所需读取能力，不执行写入、删除或上传。
- [x] AC7（R10）：开发和部署文档能指导管理员完成扫码、处理过期/失效、重新授权，并理解数据库与备份包含可用凭据的保护责任。
- [x] AC8（R5/R11）：连接页没有删除入口；同账号重新授权覆盖原凭据并保留连接 ID，账号不一致时旧连接保持不变。
- [x] AC9（R12）：侧边栏不再有独立连接管理导航；设置下方授权卡片显示连接状态，已授权时显示账号名、会员概况与已用/总容量，并可进入连接管理页。
- [x] AC10（R13）：授权后可读取并持久化非敏感会员与容量快照；连接页支持手动刷新；上游资料不完整时显示未知并保留有效连接状态。
- [x] AC11（R14）：连接资料区展示头像、用户名、UID、Cookie 方式、可确认的 VIP 状态/到期信息和容量用量；当前 Cookie SDK 未返回官方等级名称，不显示原始数字或推算名称；可读的设备数单独显示，缺失字段不冒充已知。
- [x] AC12（R6/R15）：115 上游错误码与经过脱敏的错误消息可在 API/扫码状态中到达前端并显示；Cookie、授权头、二维码参数和未经筛选的响应体不得返回。

## Out of Scope

- 115 文件浏览、搜索、上传、删除、离线下载、STRM 生成和播放解析。
- 媒体库创建、扫描任务、调度器、SSE 业务事件和媒体服务连接。
- 多个活动 115 账号、账号切换、共享连接或多用户权限。
- 自动迁移已有明文 Cookie；当前项目没有已保存的 115 凭据。
- 借用第三方公共 OAuth 回调或令牌生成服务。
- 断开或删除连接；首版只允许查看、测试和重新授权，避免在媒体库引用规则确定前引入破坏性生命周期操作。

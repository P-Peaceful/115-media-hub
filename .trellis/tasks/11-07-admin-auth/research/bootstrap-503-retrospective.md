# 复盘：SQLite 可连接，但认证表结构不兼容

## 1. 根因类别

- **E — 隐含假设**：把 goose 已应用版本 2 当成认证表结构符合规范的证据。实际被忽略的本地数据库具有不同的版本 2 结构。
- **D — 测试覆盖缺口**：全新数据库、从仅有应用结构的版本 1 升级、重启持久化均通过；但没有覆盖早期开发库已标记版本 2、表名/列名却不兼容的情形。
- **B — 跨层契约**：readiness 只检查数据库连接，而 auth bootstrap 依赖兼容的管理员/会话表结构。HTTP 返回安全 503，但没有足够的存储操作诊断。

## 2. 早先证据为何没有发现

生产/本机/容器和浏览器集成有意使用隔离的临时数据库，因此验证了当前结构安装，而不是用户现有的本地数据库。更早的开发代理 403 是独立问题；直连 8080 时 bootstrap 503 而健康检查 200，将本故障与已解决的代理问题区分开。只读检查发现 `administrators.singleton` 不存在，并发现旧会话/审计表，因此取得了实际结构证据，而不是依赖对 IDE/调试器的猜测。

## 4. 系统性推广

当迁移版本在多轮实验间复用时，所有持久化本地开发数据都有此风险。将故障归因于传输之前，先检查真实数据库结构。本任务中用户选择丢弃旧开发库；应尊重此决定，而不是擅自增加兼容逻辑。正常启动绝不自动删除持久状态。安全的失败诊断和对请求取消的正确分类，能改善实际负责该行为的边界。

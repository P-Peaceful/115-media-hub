# 115 SDK findings (planning)

Inspected the project's locked dependency `github.com/SheltonZhu/115driver v1.3.5` under the local Go module cache.

- `pkg/driver.FileListResp` exposes `Count`, `Offset`, `Limit`, `PageSize`, and the current page in `Files` (`json:"data"`).
- `Pan115Client.ListPage` calls `GetFiles` but discards `FileListResp.Count`; it returns only `[]File`.
- `Pan115Client.ListWithLimit` loops over offsets until `Count`, materializing the full directory (with its page limit capped), so it is not appropriate for browser pagination.
- Exported `driver.GetFiles(req, dirID, WithOffset(...), WithLimit(...))` returns `*FileListResp`. A project adapter can use a credential-imported driver's `NewRequest` to preserve one page and the count.
- Default list options use `show_dir=1`; keep directory visibility explicit in the adapter contract.
- `Pan115Client.Stat(id)` exposes `FileCount`, `DirCount`, and `Parents`, suitable for directory summary/path metadata. Verify actual root/parent ordering before rendering.
- `SearchOption` includes `Cid`, `Offset`, `Limit`, `SearchValue`, and `Type`; `SearchResult.Count` is surfaced. `Search` currently sets `FileCount` and `FolderCount` to zero because the underlying response type does not provide them. This distinct `/files/search` method does not expose a direct-child-only flag in the pinned SDK.
- Further research found the `/files` listing endpoint accepts `search_value`, `type`, and `cur`; `cur=1` is documented as restricting results to the current directory. Positive type/suffix filters may traverse descendants when `cur=0`, so browser search/type filters must explicitly include `cur=1`. A separate 115 SDK binding models the same `Cur` option for `/files` ([115 API parameter reference](https://p115client.readthedocs.io/en/latest/reference/module/client.html), [OpenListTeam/115-sdk-go field definition](https://github.com/OpenListTeam/115-sdk-go/blob/main/fs.go)).
- Therefore use a single paginated `/files` request for both plain listings and search/type filters, with current `cid`, bounded `offset`/`limit`, `show_dir=1`, and `cur=1`. Since the pinned SDK's `GetFiles` wrapper omits `search_value` and `cur`, use its credential-bound request/client and response types at the adapter boundary to pass those documented parameters and preserve `FileListResp.Count`.
- Follow-up debugging of the UI's false “115 connection not configured” state found that the adapter's manual request omitted SDK list defaults and used `order` instead of the SDK's `o`. In v1.3.5, `GetFiles` sends `aid=1`, `cid`, `o=user_ptime`, `asc=1`, `offset`, `show_dir=1`, `limit`, `snap=0`, `natsort=0`, `record_open_time=1`, `format=json`, and `fc_mix=0`. The adapter now mirrors those defaults and adds `cur=1` plus optional `search_value`/`type`. This is statically aligned to SDK source; the live account must still confirm upstream acceptance.

# 115 QR reference

Source: https://github.com/pancras-loe/115-station/blob/c5d308beff82448c7d223b51edae37053fe88ff5/internal/api/115.go (reference, not a dependency or official API guarantee).

The source describes token acquisition at `https://qrcodeapi.115.com/api/1.0/web/1.0/token/`, QR image at `https://qrcodeapi.115.com/api/1.0/mac/1.0/qrcode`, polling `https://qrcodeapi.115.com/get/status/`, and exchanging confirmation at `https://qrcodeapi.115.com/app/1.0/{app}/1.0/login/qrcode/`. Its comment also mentions a passportapi result endpoint; its actual constant uses qrcodeapi. Reported status values: 0 waiting, 1 scanned, 2 confirmed, -1 expired, -2 cancelled. It notes user-agent/device behavior and upstream risk controls. Verify against live service when feasible; use bounded requests, no raw secret or upstream-body logging, and do not return the resulting Cookie to the browser. These are observations, not assurances of API stability.

## Cookie-based account details

`internal/api/routes.go` in the same reference project (commit `c5d308beff82448c7d223b51edae37053fe88ff5`) requests `https://my.115.com/?ct=ajax&ac=nav` with the stored Cookie and matching 115 Browser User-Agent. It reads `user_name`, `user_id`, `face`, `vip`, `expire`, and `forever`; its code documents `vip` as 0=non-member and 1/2=member, `expire` as Unix seconds and `forever` as the permanent-membership marker. Keep the raw integer internal and render unrecognized or absent values as unknown.

The same Cookie request to `https://webapi.115.com/files/index_info` returns capacity and `login_devices_info.list`; observed device fields are `name`, `device`, `ip`, `city`, `utime` (Unix seconds) and `is_current` (1 means current device). A fresh `nav` response also serves as an authorization check: success means the Cookie is accepted, an explicit login-required response means invalid, while network or other upstream errors are inconclusive.

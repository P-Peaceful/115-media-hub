# 115 directory API research

The public reference implementation at https://github.com/ChenyangGao/p115client/blob/856e4f8f09ce034534bd458f06d3dee4474a1698/p115client/client.py documents `GET https://webapi.115.com/files` with `cid`, `offset`, `limit`, `cur`, `o`, `asc`, and `type`. It describes `cur=1` as limiting filtering to the current directory, up to 1,150 entries per page, and sorting by file name, size, or modification time. It also notes that nonexistent `cid` can be treated as root and that provider risk controls can affect this endpoint. Never treat a successful root fallback as evidence the requested directory exists: verify the returned path/cid.

The same reference warns that `/files/search` is limited to the first 10,000 results, can return short pages, and does not reliably support per-request sorting. It is therefore not sufficient by itself for the approved whole-directory search contract. A complete paginated directory enumeration with local matching is a possible approach, but resource bounds and concurrent directory changes must be addressed explicitly.

On 2026-11-10 a read-only request using the existing stored account credential to `/files?aid=1&cid=0&limit=3&offset=0&cur=1` succeeded via curl. The response included `state`, `cid`, `count`, `offset`, `data` and `path`; path entries included `cid`, `pid`, and `name`. This checked root access only, not file parsing, multiple pages, search, authorization expiry, or sorting semantics. No credential or personal file names were recorded. Python urllib in this environment failed to connect, while curl succeeded; a Go transport check remains necessary.
